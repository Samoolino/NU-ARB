How continuous scanning, execution gates, and persistence work
            
The engine opens a WebSocket order-book watcher for each configured market symbol and reconnects with backoff. It ranks cross-venue buy/sell directions when books change; a live attempt must still pass fresh-book, depth, balance, fee, permission, IOC-route, latency, and risk checks immediately before submission. The UI shows the latest per-venue books plus aggregate subscription/receipt/freshness counts; it does not render every depth delta.

            
REST is not a second continuous order-book stream: the engine samples REST server-time RTT at preflight and periodically during a run. The public scanner separately takes REST snapshots. The browser polls authenticated engine state and journal APIs; it does not maintain exchange sockets. A target is a realized-PnL stop threshold, not a promised profit.

            
Code: arb_bot/arbx/market.py (WebSocket books and RTT sampling), worker.py (per-venue lifecycle and health), hub.py (cross-venue ranking and gates), execute.py (IOC executor), journal.py (durable SQLite outcomes), web_api.py (/api/v1/engine/state and /api/v1/engine/journal); this board is in index.html and public/index.html.
